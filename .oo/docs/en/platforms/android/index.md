# Android platform

[简体中文](../../../platforms/android/index.md)

Android uses a non-UI foreground Supervisor to manage multiple logical V8 runtimes. Each Runtime has its own engine, runtime thread, generation, NativeHost, output sequence, and Inspector socket.

The Service owns ADB discovery, installation, command-v2 transport, forward/reverse leases, log consumption, and recovery. The device exposes no TCP control listener. Full commands stay in the app-private directory, while the exported compatibility ingress accepts only a random command ID.

The current isolation mode is `runtime`: logical V8 isolation inside one Android application process. `isolatedProcess` returns a stable unsupported error.

Embed the production [`runtime-host` source SDK](../../../../../adapters/android/runtime-host/README.md) in your own Android app, not the E2E APK. It packages the shared Runtime and production bootstrap without diagnostic controls, fixtures or Linux images. It requires API 29+, JDK 17, SDK 35 and pinned Javet 5.0.10; the AAR is not a single-file SDK containing every transitive dependency.

The Host may explicitly install a fresh `crypto-host` per generation for synchronous SHA-1/SHA-256, HMAC-SHA-256, AES-256-GCM, entropy and timing-safe comparison; it is absent by default. Optional [`storage-host`](../../../../../adapters/android/storage-host/README.md) supplies persistent binary KV through the shared Policy/Broker and an asynchronous native worker. Its logical namespace is `default`; SQLite and credentials remain unsupported. Adding a module grants no authority. Both run shared JS contracts and generation-recreation tests through the production bootstrap on an API 35 arm64 emulator, not a physical device.

The network provider independently enforces authority, DNS address admission, socket/TLS behavior, quotas, cancellation, and streaming credit. The shared JavaScript Runtime still owns Fetch, redirect, Request, Response, and Abort semantics.

Android accepts Host-provided `holo-plugins:///` Bundles before startup. Javet uses a read-only static plugin manifest generated by the Host and synchronously installs Cordis Contexts in a Host V8 realm isolated from the Guest; plugin globals are not visible to Guest code. Promise-returning asynchronous initialization fails before Guest entry. Static synchronous plugins can intercept Capability calls; live plugin-graph replacement and `--watch` are not currently supported.

`v8-host` provides a narrow Engine Gate JNI bridge for the pinned Javet 5.0.10/V8 ABI. The application supplies a fresh
Host Gate for every generation through `RuntimeEngineFactory.create(engineGateFactory = ...)`. The bridge synchronously
submits a source digest and safe copy from the real V8 string and Wasm compilation callbacks; a denial or Host exception
fails closed. It neither reads Javet's private object layout nor owns permission UI. Emulator evidence covers per-operation
allow/deny, zero generated-code side effects after denial, and rebinding a fresh Gate after restart. Loader, Inspector, and
Observer features not declared by the Android capability descriptor remain unavailable.

The optional production `process-backend-v86` module provides the Experimental v86 track. The Android Host assembles
`AndroidV86RuntimeServicesFactory` while creating a Runtime. Process access `none` reads no assets and creates no extra
V8. Selecting `experimental.v86-v1` with `sandboxed` access automatically installs process-wide Liftoff-only flags.
Each root child owns one trusted V8/Linux VM in the `processTree` scope; shared `runtime` VMs are currently denied.
Assets are explicitly packaged with
`-Pholonomy.v86.assetsDir` or `HOLO_V86_ANDROID_ASSET_ROOT`; the core Android modules do not unconditionally carry the
roughly 37.9 MiB raw `agent` Linux asset set.

The upgraded image has passed 13 shared JS contract cases on an API 35 arm64 emulator, covering the standard `node:child_process` facade, Linux-PID attribution, `/workspace` FUSE, stdio, TCP/UDP/DNS, Device/System projection and a fresh generation. It denies later Guest exec and fork/clone; the old image's descendant allow/deny evidence is not current support. Physical-device acceptance remains open.
An instrumentation APK is only the separate test
package installed beside the app under test and launched by AndroidJUnitRunner; the Backend being exercised comes from
the production AAR. This combination remains Experimental and does not claim physical-device support, a POSIX
filesystem outside `/workspace`, 64-bit, multicore, or true VM snapshot/restore.

Emulators and physical devices use the same product path, but acceptance reports must identify them separately. Emulator evidence cannot be reported as physical-device evidence.
